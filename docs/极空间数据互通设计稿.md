**结论**：现有"单向备份"是**每设备隔离的文件快照**，不产生可供合并的共享记录。因此 ②双向 / ③恢复 / ④协同**无法靠扩展 `backupAll` 实现**，必须新增一层**共享记录层**。

## 1. 总体方案：双轨并存

```
/dav/壹ZHANG核/
  pc/            ← 既有安全快照（保留，不动）
  pura_xmax/     ← 既有安全快照（保留，不动）
  shared/        ← 【新增】合并记录层，所有设备读写同一份
```

- **轨 A（安全快照）**：沿用 `backupAll`，每设备一份全量文件备份，作为兜底/灾难恢复。**不在本稿改动。**
- **轨 B（共享记录层 `shared/`）**：新增 `SyncOrchestrator.syncRecords()`，按记录（行）级别做增量推送/拉取与冲突合并。②–④ 全部建立在轨 B 上。
- 二者并存、互不破坏：旧版本 app 只认 `pc/` `pura_xmax/`，会忽略 `shared/`（无害）；新版本两者都维护。

## 2. v4 本地 schema（P1–P3 的硬地基）

### 2.1 新增列（在现有 `walnut` / `item` / `patina` 三表各加）

```sql
ALTER TABLE walnut   ADD COLUMN updated_at INTEGER NOT NULL DEFAULT 0;
ALTER TABLE walnut   ADD COLUMN rev        INTEGER NOT NULL DEFAULT 0;
ALTER TABLE walnut   ADD COLUMN is_deleted INTEGER NOT NULL DEFAULT 0;
-- item / patina 同理
```

- `rev INTEGER`：**本地单调递增计数器**，每次本地增/改/删（→置墓碑）自增 1。排序与冲突判定**只用 rev + deviceId 决平**，不依赖墙钟（避免 PC/华为 NTP 偏差）。
- `updated_at INTEGER`：epoch ms，仅用于展示"最后修改"，不参与合并判定。
- `is_deleted INTEGER`：软删墓碑。物理删除改为 `UPDATE ... SET is_deleted=1, rev=rev+1`。

### 2.2 新增本地元表 `sync_meta`

```sql
CREATE TABLE sync_meta (
  key TEXT PRIMARY KEY,
  value TEXT
);
-- device_id      : 首次运行生成的 UUID（每安装唯一）
-- last_push_rev  : 已推送的最大 rev
-- last_pull_rev  : 已拉取处理的最大 rev
```

### 2.3 迁移（`database.dart` `onUpgrade`）

```dart
if (oldVersion < 4) {
  for (final t in ['walnut', 'item', 'patina']) {
    await db.execute("ALTER TABLE $t ADD COLUMN updated_at INTEGER NOT NULL DEFAULT 0");
    await db.execute("ALTER TABLE $t ADD COLUMN rev INTEGER NOT NULL DEFAULT 0");
    await db.execute("ALTER TABLE $t ADD COLUMN is_deleted INTEGER NOT NULL DEFAULT 0");
  }
  await db.execute("CREATE TABLE sync_meta (key TEXT PRIMARY KEY, value TEXT)");
}
```
> 既有行 `rev=0`；首次同步时 `last_push_rev=0` → 全量上传（幂等 PUT，安全）。**该迁移会触碰 `database.dart`（用户正在审查），故代码实现必须等 #35 通过后。**

### 2.4 rev 自增的落点（实现期关键点）

所有写操作**收口到 DAO**：`walnut_dao / item_dao / patina_dao` 的 insert/update/delete 内统一 `rev = (SELECT MAX(rev) FROM t) + 1` 并写 `sync_meta.last_push_rev`。新增/编辑表单（`add_walnut_sheet` 等）经 DAO 落库即自动 bump，无需各自改。这是 P1 实现期对现有代码最大的一块侵入，须放在 V2 验收之后。

## 3. 远端共享记录层布局（`shared/`）

```
shared/
  meta.json              # { schemaVer, devices:[{id,label}], pullCursor }
  walnut/<id>.json       # { rev, deviceId, updatedAt, isDeleted, data:{...} }
  item/<id>.json
  patina/<id>.json
  images/<ownerType>/<ownerId>/<file>   # 原图镜像，按 hash 去重
```
- 每条记录一个 JSON 文件，**整文件 PUT（幂等）**，远端即权威副本。
- `images/` 复用现有 `ImageStore` 的 `images/patina/{ownerType}/{ownerId}` 段规则，按内容哈希去重，避免同一图多端重复上传。

## 4. `syncRecords()` 设计（轨 B 核心）

```
SyncResult syncRecords(localRoot):
  cfg = SyncConfigStore.load(); client = ZSpaceAdapter.connect(cfg)
  dev = SyncMetaStore.deviceId; pushRev = SyncMetaStore.lastPushRev; pullRev = SyncMetaStore.lastPullRev
  mkcolRecursive(remoteRoot/shared)

  # —— 推送：本地 rev > pushRev 的行 ——
  for row in DAO.listChanged(revGt: pushRev):          # 含 is_deleted=1 的墓碑行
      put("/shared/<type>/<row.id>.json", serialize(row))   # 用 WebDavClient.put
      pushRev = max(pushRev, row.rev)
  SyncMetaStore.lastPushRev = pushRev

  # —— 拉取：远端 rev > pullRev 的记录 ——
  for type in [walnut, item, patina]:
      items = client.propfind("/shared/<type>", depth:1)    # 已有 propfind
      for it in items:
          remote = deserialize(get(it.href))                 # 已有 get
          if remote.deviceId == dev: continue                # 回声抑制：跳过自己写的
          local = DAO.byId(type, remote.id)
          if local == null:                upsert(remote)     # 含 isDeleted→置墓碑,不物理删
          elif remote.rev > local.rev:     applyRemote(remote) # LWW（见 §5）
          elif remote.rev == local.rev && remote.deviceId != dev: resolveConflict(remote)  # 同 rev 双改
          # 其余：本地更新，下轮推送覆盖
          pullRev = max(pullRev, remote.rev)
  SyncMetaStore.lastPullRev = pullRev
  SyncMetaStore.devices = union(已见 deviceId)              # 维护设备名册（供墓碑 GC）
  return SyncResult(uploaded, downloaded, skipped, failed, errors)
```

- **回声抑制**：`remote.deviceId == dev` 直接跳过，避免把自己刚推的再拉回来。
- **失败降级**：复用 `backupAll` 既有策略——单记录失败入 `errors` 不中断整体。

## 5. 冲突与删除语义（⚠️ 待用户拍板）

个人单主、多设备（PC+华为）场景，同一条记录同时被两端改的概率极低。建议默认策略：

| 情形 | 建议 | 说明 |
|---|---|---|
| 远端 rev > 本地 rev | **LWW 采用远端** | 自动、无提示 |
| 同 rev、deviceId 不同（双端同刻各改） | **按 deviceId 字典序决平**（或弹窗让用户选） | 概率极低；默认自动决平即可 |
| 一端删除、一端未动 | **墓碑胜**（is_deleted=1 生效） | 故意删除不应被复活 |
| 一端删除、一端编辑 | **删除胜**（保守） | 避免已删项被编辑"复活"；如需"编辑胜"请指明 |
| 两端都删除 | 删除 | 一致 |

> **待确认**：① 默认 LWW 自动（推荐）还是字段级合并（价格/备注分别合）？② 删除 vs 编辑 谁胜？

## 7. P2 回拉 / 换机恢复

- 新增 `SyncOrchestrator.restoreAll(localRoot)`：首启检测本地空库 → 提示「从极空间恢复」。
- 全量拉取 `shared/*`（非增量），按 §4 规则 upsert，**墓碑行置 `is_deleted=1` 不物理删**。
- 缺失原图按 hash 从 `shared/images/` 下载到 `ImageStore` 路径（已存在同 hash 跳过）。
- 一致性校验：记录数吻合 + 原图文件存在 + 复用 `integrity` 思路比对大小。
- **恢复源是 `shared/`，不是 `pc/` 快照**（快照是每设备隔离的，无法跨设备合并）。
- 可选墓碑 GC：确认所有已知设备 `lastPullRev > 墓碑 rev` 后物理清除（保守，后做）。

## 8. P3 多端协同查看（诚实约束）

- **硬约束**：极空间 Z2PRO 的 WebDAV **只有拉/轮询，无 webhook / 推送 / 通知**。因此"实时"不可达，现实是**近实时环境同步**。
- 机制（基本复用 `syncRecords()`，新增主要是调度与 UI）：
  - **推**：每次本地写入 → `rev+1` → 应用 resume / 下一次同步即带上（可加防抖后台触发）。
  - **拉**：应用回到前台时拉一次 + 后台周期性（如每 15–30 分钟，`Workmanager` / `flutter_background_service`）拉一次。
  - **状态条**：「已同步 / 同步中 N 项 / 最后同步 12:30」。
- **预期延迟 = 轮询间隔（≤30 分钟），非秒级**。若需真·实时，须 Z2PRO 暴露推送 API（固件相关，超出本稿）。
- P3 几乎无新同步逻辑，主要是调度 + UI，风险最低。

## 9. 安全项（建议 P1 前完成）

`SyncConfigStore` 当前 `shared_preferences` **明文存密码**（含 `trustSelfSigned`）。多设备互通后凭据会跨端存在，明文风险上升。建议迁 `flutter_secure_storage`（Android Keystore / Windows Credential Manager）。`config_store.dart:7` 已自承此债。
